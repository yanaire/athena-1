# Athena UI capability audit

Audit date: 2026-11-25. Source baseline: `6d38a5c0def941b00fc98f2d9eabdeabe60ab72f`.
The UI follow-up is on `feature/athena-workflow-dag`.

This is a source and wiring audit, with targeted DOM contracts. It is not proof of a rendered browser flow, a native Mac run, or real ChatGPT-account inference. A visible menu item is not evidence that its service exists. Browser QA and Mac acceptance must record their own exact candidate SHA and observed results.

## Historical findings at the audit baseline

1. The surface picker previously presented Browser, Device, Files and Diff without their capability limits. Runtime rows now show the relevant limited or unavailable state before opening the view.
2. Device previously instructed the user to connect a computer or lab server, although no connection action or service exists. It now explicitly states that device connection is not implemented and links to the actual Workflow view.
3. Browser previously promised that links open in a new tab. That only describes a web browser environment: the native window policy uses `NewWindowResponse::Deny`. The panel now explains the desktop limitation, provides a validated address-copy action and distinguishes link opening from agent browsing.
4. Runtime Files and Diff now link to actual available workspace views instead of leaving the user at a dead end. These links do not create file or repository permissions.
5. The Browser sample was already removed by the runtime render path at the baseline. It was not an observed runtime sample leak. The follow-up builds the sample only for preview mode and verifies that toggling into runtime removes it.

No new device, browser, shell, filesystem or network capability was added by these changes. Actual user messages and task identities in persisted state are unchanged.

## Validation scope

Targeted command:

```sh
node --test athena-backend-handoff/athena-codex-ui/qa/surfaces-capabilities-test.cjs
```

Five DOM checks cover the unavailable-feature labels, preview/runtime separation, navigation to available views, HTTP(S) validation, and copying an address when a new-window request yields no usable window. These tests use LinkeDOM, a synthetic clipboard and a stubbed window opener. They do not establish that a native browser launched, a remote device connected, CSS rendered correctly, or an actual account inferred.

The native Browser limitation is established by code inspection of `on_new_window` and `on_navigation`. Those policies are shared by the macOS and Windows desktop builds. They should be rechecked if the desktop opener contract changes. The latest source baseline's real-account native acceptance remains separate from this document; matching candidate evidence is required before a release merge.

The report records Chromium `151.0.7922.34`, Playwright `1.62.1`, Node `24.22.3`, and Linux x64. All fourteen browser scenarios passed, including both capability panels and copying an address without navigation. Visual review of all eleven screenshots confirmed readable chat, graph and result panels, a usable narrow overlay at 760 px, and visible capability limits. This is actual rendered Chromium evidence with a controlled model provider and real host/MCP execution. It does not establish Windows WebView2, macOS WKWebView, real-account inference, device pairing, or agent browser automation. The local follow-up environment permitted TCP but denied UNIX sockets; its separate fixture-smoke run passed both real calculation/download checks and is not counted as another browser run.
